# Internationalisation

Hrček for iOS speaks English (the source language) and Slovenian, from
the first screen on.

## Writing translatable strings

String Catalogs (`Localizable.xcstrings`) hold the translations, and
the English text itself is the key, so code reads naturally:

```swift
Text("Sign in")                                   // in a view
L10n.string("Saved")                              // in HrcekKit
.navigationTitle(locale.string("Sign in to Hrček"))  // text UIKit draws
```

There is one catalogue per target: `Hrcek/`, `HrcekShare/` and
`HrcekKit/Sources/HrcekKit/Resources/`. Strings in HrcekKit go through
`L10n.string`, which looks them up in HrcekKit's catalogue rather than
the app's, in the language in use.

## The language in use

People choose the language in the app: Automatic, English or
Slovenščina. `LanguageModel` keeps the choice in the shared Keychain
group (`KeychainLanguageStore`), the only storage app and share
extension share, and sets `L10n.choice`. `L10n.language` resolves it:
the choice, else the phone's first language there is a translation
for, else English. It is also what `Accept-Language` asks the server
for.

Both processes put the resolved locale in SwiftUI's environment
(`.environment(\.locale, …)`), which `Text` and most controls follow.
A navigation title drawn large by UIKit does not; resolve it with
`Locale.string(_:)` from the environment's `locale` instead. The share
extension reads the choice each time it opens, so a change in the app
applies to the next share.

iOS's own per-app language (Settings › Apps › Hrček › Language) does
not reach the share extension, which runs as its own process, so it is
not relied on.

## Plurals

Never assemble a count by hand. Interpolate it, and give the entry
plural variations in the catalogue. Slovenian has four forms, chosen
by the last two digits:

| Form | Counts | Example |
|---|---|---|
| one | 1, 101, 201 … | 1 vnos |
| two | 2, 102 … | 2 vnosa |
| few | 3, 4, 103 … | 3 vnosi |
| other | 0, 5–100 … | 5 vnosov |

`PluralTests` in HrcekKit checks the toolchain applies these rules.

## After changing a string

```bash
scripts/translations            # adds new keys, marks removed ones stale
scripts/translation-status      # lists what still needs Slovenian
scripts/translate Hrcek/Localizable.xcstrings "Sign in" "Prijava"
scripts/translate CATALOG "%lld entries" \
  --plural one=… two=… few=… other=…
```

`scripts/translations` builds the app, takes the strings the compiler
found, and syncs every catalogue with them. It runs as a commit hook,
as a fixer: if a catalogue lagged the source, the hook updates it and
the commit stops, so the new strings can be translated and added. Stale
entries — strings no longer in the code — are reported by
`translation-status`; delete them from the catalogue.

You can also edit catalogues in Xcode's catalogue editor.

## Incomplete translations

`translation-status` never fails: a gap is a nudge, and on CI it
becomes a warning on the run. An untranslated string shows in English.
Unlike gettext's `fuzzy`, an iOS string marked *needs review* is still
shown, so mark machine translations that way and review them before a
release.
